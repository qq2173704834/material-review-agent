- 现象：用户更新材料后点击“执行审查”进入页面，看到上次失败结果；手动点击“全量复检”后才更新。用户需要猜测第二个入口才能真正开始新一轮。
- 预期：阶段标签只负责切换，按钮明确区分“查看上次结果”和“重新检查”。更新材料后主操作直接提供重新检查；执行中显示进度，完成后切到新结果。不以旧执行的“已完成”表达当前材料已检查完成。
- 费用边界：普通进入页面、切换标签、刷新和查看历史不能偷偷触发真实模型调用；由明确的重新检查操作启动，防重复提交。开始新执行不修改旧执行快照。
- 验收：新材料有缺项→修改补齐→上传→明确提示待复检→一次点击重新检查→显示最新有效结果；旧URL指定execution时应提示历史查看，不能覆盖当前结果状态；报告导出遵守同一有效性规则。

## UXR-043 结果优先与简版自查报告

- 状态：代码已实现并通过本地隔离核对；云端发布及用户复核见实施验收保留条件。
- 用户反馈：报告开头大段任务/执行ID、规则集、模型模式、时间戳等技术内容，用户关心的“材料是否符合要求”被排在后面。希望精简报告，或直接反馈结果。

- 页面与简版报告采用相同顺序：整体结论→需要修改的问题与做法→未能确认的事项（有才显示）→少量基本信息。基本信息只保留可读的任务/考试短名称、实际被检查的文件名和北京时间检查时间；长通知正文首句不直接充当大标题。
- 整体结论规则：依据当前有效执行计算。“通过本次自查”仅用于适用必需项均已检查通过且无影响整体结论的未知/未执行；存在必需项失败显示“需要修改”；关键项待确认或无法检查时明确显示“部分内容待确认”；未执行完成、失败或取消不能显示全部合格；材料更新后显示“材料已更新，待重新检查”。这些是展示摘要，不新增或替代原五类逐项判定。
- 建议/可选项单独呈现为“可改进项”，不自动将其不满足算成必需项不合格；不适用项不充当通过项凑数。
- 默认省去：任务/执行/规则集UUID、解析状态枚举、内部版本编号、来源快照清单、精确毫秒时间、模型厂商名称和Token/请求明细；逐项通过结果可用一句概况表达，问题列表聚焦需要处理的内容。对应调试与审计数据仍留在受限服务端记录。

- 说明：用一行“结果仅供材料准备参考，以组织方审核为准”表达自查性质；模拟、未完成、未完整读取、待复检等影响结论的状态必须明确，不因文案精简而省略。
