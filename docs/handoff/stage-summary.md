## 2. 产品定位

用户提供通知、项目指南、要求文件或网页链接，Agent 自动理解本次提交要求，匹配用户上传的材料，逐条检查，并给出有证据的问题说明、整改建议与复检结果。

产品面向不同领域的材料提交场景。规则来自当前任务的要求来源，不预先写死某个比赛、奖学金或申报项目的专用规则。首版可以限制支持的文件类型与检查能力，以保证结果可靠。

### 一句话介绍

一个读懂通知和项目要求的通用材料预审 Agent：自动提取提交规范，匹配用户材料，逐项核验，并提供可追溯的问题说明、整改建议与复检报告。

### 用户价值

- 减少从长通知和附件中整理要求的时间。
- 发现漏交、错交、格式不符和跨材料信息冲突。
- 让每项结论能够同时核对要求原文和材料证据。
- 通过修改后的复检，确认问题是否已经解决。

### 主流程

创建审查任务 → 导入要求 → 提取规则 → 补充必要信息 → 上传并匹配材料 → 执行检查 → 查看结论与证据 → 修改材料 → 复检 → 导出报告。

用户可以一起提供要求和材料。只有影响判定的条件不明、要求冲突或必要信息缺失时，才提出针对性问题，不要求每次手动确认完整规则表。

### 一次任务的核心数据

要求来源、任务背景、规则及版本、材料及版本、规则与材料的匹配关系、执行记录、证据、检查结论、整改和复检记录。

### 检查结论

| 状态 | 含义 |
| --- | --- |
| 通过 | 有足够证据支持符合要求 |
| 未通过 | 有明确依据表明不符合要求 |
| 待确认 | 条件、规则或材料存在歧义 |
| 无法检查 | 解析、访问或能力限制导致无法核验 |
| 不适用 | 当前任务不满足要求的适用条件 |

未开始、执行中、已取消属于执行状态，不与上述结论混用。没有检索到证据不自动等于内容缺失；部分解析或未执行项目不能计为通过。

### 建议优先打磨的体验

1. 从此前未专门配置过的通知中生成规则。
2. 文件属性交给程序检查，语义内容结合证据检查。
3. 点击问题同时定位要求原文和材料证据。
4. 替换修订材料后显示已解决、新增和仍存在的问题。

完整视频理解、源码运行、自动提交、多人协作等不是目前首版核心承诺。

## 6. 已确定的开发规则

### 编码与命名

- 参考华为公开规范，适配 Web 项目。
- 华为 iBMC Web 编码规范页面已定位，但本次访问被拒绝，尚未读取全文。
- 已读 OpenHarmony 应用 TS&JS 编程指南，不能将社区指南等同于华为全部内部标准。
- 使用英文见名知意，参考 openGauss；避免拼音、模糊名称与不必要缩写。
- 变量与函数 camelCase；类型与 React 组件 PascalCase；固定共享业务常量 UPPER_SNAKE_CASE。
- 布尔值表达判断语义，数值注明单位，例如 hasEvidence、timeoutMs、fileSizeBytes。

### 开发节奏

按功能推进：明确验收点 → 实现功能及相关必要测试 → 执行相关验证 → 检查差异 → 按约定提交。

每个 commit 尽量对应单一功能、可独立说明的子项或独立缺陷。避免混入无关重构与格式化。大功能可以拆为多个可验证的小提交。

### 已选 commit 格式

```text
[类型(编号)]: 中文摘要

目的：为什么进行本次修改。
变更：实现或修复了什么。
验证：实际执行的检查及结果；未执行时说明原因。
```

标题示例：

```text
[feat(M01)]: 支持批量上传材料
[fix(BUG-001)]: 修复可选材料被误判为缺失的问题
```

BUG-001 为格式示例，尚未建立该缺陷记录。实际提交使用真实需求、缺陷或工程任务编号。此格式按用户要求定制，不直接套用 Conventional Commits 默认校验器。

## 7. 网页功能测试工具

用户要求提供可复用小工具，集中放在 tests/。计划采用 Playwright UI 配合项目命令，支持按功能或场景运行，准备测试样例，查看实际浏览器操作及失败原因。

```text
tests/
  README.md
  fixtures/
  e2e/
  helpers/
  mocks/
  scripts/
```

拟提供 test:ui、test:e2e、test:report 三个 pnpm 命令，当前尚未实现。

模拟模式用于稳定检查页面、流程与异常状态；真实 AI 联调单独启用，验证实际模型、解析及检索链路。报告标明模式，不能将模拟通过描述为真实链路验证通过。

测试使用合成材料与独立任务；固定用例进入版本控制，运行报告、截图、临时文件和凭据默认不提交。关键 bug 修复补充回归场景。测试工具随功能开发逐步完善。
