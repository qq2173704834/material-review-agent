# 项目开发约定与提交模板

更新日期：2026-11-11。当前为开发前约定，后续随用户补充更新。

配套文件：stage-summary.md 为阶段总结；requirements.md 为保留原有编号的详细需求与验收计划。本文记录工程规则，不代表应用已经实现。

## 已明确的用户要求

1. 技术栈从比赛通知的推荐技术中选择。
2. 编码规范参考华为代码规范，核实实际来源与适用范围。
3. 按功能开发，commit 尽量对应单一功能；修复 bug 单独使用 fix 提交。
4. commit 参考 openGauss-server 的第三种示例并加方括号，统一为 `[类型(编号)]: 中文摘要`，正文附修改与验证说明。
5. 提供方便测试网页各功能的小工具，测试代码、样例与辅助脚本集中在 tests/，随功能开发逐步完善。
6. 变量命名尽量使用英文、见名知意，参考 openGauss 仓库，结合本项目语言进行适配。

## 命名规则

遵循用户要求：使用含义明确的英文命名，参考 openGauss 仓库。以下具体写法是适用于本项目 TypeScript/React 的约定及示例，不作为 openGauss 官方逐条规范引用。

| 对象 | 约定 | 本项目示例 |
| --- | --- | --- |
| 变量 | camelCase，描述业务含义 | requirementSource、uploadedMaterials |
| 函数 | camelCase，表达动作与对象 | extractRequirements、validateFileFormat |
| 布尔值 | 按语义使用 is/has/can/should | isApplicable、hasEvidence、canRetry |
| 类型与组件 | PascalCase | ReviewTask、EvidencePanel |
| 共享业务常量 | UPPER_SNAKE_CASE | MAX_UPLOAD_SIZE_BYTES |
| 带单位数值 | 显式包含单位 | fileSizeBytes、timeoutMs |

普通 const 局部变量仍使用 camelCase，不因 const 声明就全部大写。集合名称应体现复数或集合含义，领域术语保持一致。避免拼音、含义不明的缩写，以及在复杂上下文中使用过于宽泛的 data、info、temp、obj。短循环索引或生态中约定俗成的缩写可以合理使用。

## 开发与提交原则

- 按功能依次开发：明确目标和验收点，完成实现，进行相关验证，检查差异，再按约定提交。
- 每个提交尽量对应一个功能或独立缺陷；一个功能包含相关代码、必要测试和文档是合理的。
- 大功能按有意义且可验证的子项拆分，不要求所有功能都只能有一个提交。
- 新功能使用 feat，修复使用 fix；修复标题描述具体问题，不使用单独的“fix bug”。
- 不把无关重构或全项目格式化混入功能提交。
- 验证说明只记录实际执行结果。未执行的检查必须写“未运行”及原因。
- 以下为已选定格式，示例仅用于说明写法，不代表功能或测试已完成。

## 已选提交格式

参考官方主仓库 https://atomgit.com/opengauss/openGauss-server 中实际出现的 `fix(IBI4Z0): 修复复合 token 报错问题`，按用户要求为完整前缀加上方括号。本项目统一格式如下：

```text
[类型(编号)]: 中文摘要

目的：说明本次功能目标或需要解决的问题。
变更：说明主要实现或修复内容。
验证：记录实际执行的检查及结果；未运行时说明原因。
```

具体规则：

- 方括号包住“类型(编号)”，冒号位于右方括号之后，冒号后空一格。
- 标题与正文之间空一行，正文使用“目的：”“变更：”“验证：”三个固定字段，需要时在字段下分条说明。
- 编号对应真实的需求、缺陷或工程任务，不使用模块名冒充编号，不伪造 Issue 或验证结果。
- 标题概括一个功能、功能子项或独立问题，避免“更新”“fix bug”等含糊描述。
- 此格式为本项目适配结果。后续如引入提交信息校验器，使用对应的自定义解析规则，不直接使用 Conventional Commits 默认格式校验。

新增功能示例：

```text
[feat(M01)]: 支持批量上传材料

目的：允许用户一次上传多份待检查材料。
变更：新增批量上传入口、文件校验和逐文件进度展示。
验证：填写实际执行的测试场景与结果，未执行时说明原因。
```

缺陷修复示例（BUG-001 为格式示例编号，尚未建立该缺陷记录）：

```text
[fix(BUG-001)]: 修复可选材料被误判为缺失的问题

目的：纠正必交要求与可选要求的判定混用。
变更：仅对适用的必交规则生成材料缺失问题。
验证：填写必交、可选和条件规则场景的实际验证结果。
```

## 通用提交类型

| 类型 | 用途 |
| --- | --- |
| feat | 新功能 |
| fix | 缺陷修复 |
| refactor | 不改变外部行为的重构 |
| perf | 性能优化 |
| docs | 文档更新 |
| test | 测试变更 |
| style | 不改变逻辑的代码格式调整 |
| build | 构建或依赖配置 |
| ci | 持续集成配置 |
| chore | 不属于其他类型的工程维护 |

括号内使用关联编号；涉及的模块可以在摘要或变更说明中写明。页面视觉样式的功能变更按实际用途使用 feat 或 fix，不混同于代码格式化的 style。

## 网页功能测试工具约定

### 目标与实现方式

提供可重复使用的测试入口，让用户选择功能或场景，准备样例、执行网页操作、查看断言结果和失败原因。

工作方案是 Playwright UI 加项目测试命令，复用其可视化用例选择、浏览器调试和报告能力。Playwright 属于补充的测试基础设施，比赛通知未指定该工具。tests/ 指工程文件夹，不等于在业务网站公开 /test 路由。

### 功能要求

| 能力 | 约定 |
| --- | --- |
| 按功能运行 | 可选规则导入、材料上传、检查执行、证据查看、整改复检、报告导出等功能组 |
| 按场景运行 | 可执行单条场景、整个功能或核心流程；新增场景与对应功能关联 |
| 准备样例 | 提供合成通知、合规及不合规材料、损坏文件等适用样例，注明预期结果 |
| 浏览器验证 | 实际操作页面，检查上传反馈、状态变化、结果展示与主要交互 |
| 模拟 AI 模式 | 使用固定响应验证界面和流程，模拟超时、失败等异常，避免普通页面测试反复调用模型 |
| 真实 AI 联调 | 单独启用真实模型与真实解析链路，明确标注模式；按预期事实、证据与结构判断，不要求生成文字完全一致 |
| 失败排查 | 提供失败步骤、断言差异、必要截图和调试轨迹 |
| 重复执行 | 测试数据相互隔离，可重置测试创建的数据；不删除用户真实数据 |
| 测试报告 | 显示通过、失败、跳过和未执行，注明环境、模式与时间 |

模拟 AI 模式的成功仅证明被覆盖的页面或流程行为，不能代表真实模型、外部网络、文档解析和检索质量已经通过验证。真实端到端用例与模拟用例须能明确区分。

### 目录规划

以下结构将在应用工程创建后建立，当前尚未生成实际测试工具：

```text
tests/
  README.md        使用方法、环境准备、模式说明
  fixtures/        合成通知与测试材料
  e2e/             按功能分组的浏览器测试
  helpers/         数据准备、页面操作和清理辅助函数
  mocks/           可控的 AI 与外部服务模拟响应
  scripts/         测试启动和样例生成等辅助工具
```

拟提供的运行入口：

```text
pnpm test:ui       打开可视化测试界面，选择功能或场景
pnpm test:e2e      执行浏览器自动化测试
pnpm test:report   查看最近一次测试报告
```

命令、依赖和配置尚未实现，将在工程初始化与功能开发阶段补齐。固定样例和测试代码进入 Git；运行生成的报告、截图、临时文件与凭据默认忽略。

### 与开发流程的关系

每个功能明确主要验收场景，实现功能并补充必要用例，再执行相关测试，最后将真实验证结果写入 commit。修复关键 bug 时补充能够复现该问题的回归场景。测试随功能积累，避免为简单样式修改添加只重复实现细节的测试。
