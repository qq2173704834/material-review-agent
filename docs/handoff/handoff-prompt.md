## 二、产品定位——必须保持准确

我要做的是一个“由具体通知或项目要求驱动的通用材料预审 Agent”。

用户提供某个通知、项目指南、要求文件或网页链接，网站自动获取并理解其中的材料提交要求，再对照用户上传的文件和链接检查是否符合要求，输出有依据的问题说明、整改建议和复检报告。

同一套系统可以处理比赛提交、项目申报、奖学金申请等不同场景。通用性体现在检查规则来自当前输入，并由可复用检查能力执行。不要将某一比赛的要求写死在业务代码中，不要退化为只返回一段意见的聊天框，也不要承诺第一版能够核验所有文件格式与真实性问题。

一句话介绍：一个读懂通知和项目要求的通用材料预审 Agent，自动提取提交规范、匹配用户材料、逐项核验，并提供可追溯的问题说明、整改建议与复检报告。

核心流程：

创建任务 → 导入要求 → 提取规则 → 补充必要信息 → 上传并匹配材料 → 执行检查 → 查看结论与证据 → 修改材料 → 复检 → 导出报告。

用户可以同时提供通知与材料。默认自动处理；只有关键歧义、冲突或影响条件判断的信息缺失时才询问，不要求每次人工确认所有规则。

最需要打磨的能力：

1. 将自然语言要求转为可执行的独立检查项。
2. 根据要求选择检查工具，结合检索到的材料证据判断。
3. 点击问题能查看要求原文与材料证据。
4. 材料修改后能够复检，并跟踪问题是否解决。

## 五、编码与命名规范

用户要求“代码规范参考华为代码规范；变量命名尽量英文、见名知意，参考 openGauss 仓库”。

参考来源：

- 华为技术支持 JavaScript 编码规范入口：https://support.huawei.com/enterprise/zh/doc/EDOC1100157892/b92a0c7c 。旧会话定位到该页，但访问被拒绝，未读取全文。
- 已读的 OpenHarmony 社区《应用 TS&JS 编程指南》：https://gitcode.com/openharmony/docs/blob/OpenHarmony_feature_Release_20250728/zh-cn/contribute/OpenHarmony-Application-Typescript-JavaScript-coding-guide.md 。它是 OpenHarmony 社区指南，不能描述为华为全部内部规范。
- openGauss 主仓库：https://atomgit.com/opengauss/openGauss-server 。

采用适合 Web 的规则，旧规范中与当前工具链冲突或特定运行环境相关的条款需要记录适配原因。不要照搬 C/C++ 风格或声称项目补充规则是官方原文。

项目具体约定：

- 变量与函数 camelCase：requirementSource、uploadedMaterials、extractRequirements。
- 类型与 React 组件 PascalCase：ReviewTask、EvidencePanel。
- 固定的共享业务常量 UPPER_SNAKE_CASE：MAX_UPLOAD_SIZE_BYTES；普通 const 局部变量仍用 camelCase。
- 布尔值按语义使用 is/has/can/should：isApplicable、hasEvidence、canRetry。
- 数值显式写单位：fileSizeBytes、timeoutMs；集合名体现集合或复数含义。
- 英文名称清楚表达业务，避免拼音、含义不明的缩写和在复杂上下文中泛用 data/temp/obj；允许常见缩写和简短循环索引。
- 优先 const，需要重新赋值时用 let，避免 var。
- 明确 null/undefined 类型，函数返回类型明确，使用 import type/export type。
- 外部未知数据先视为 unknown 并验证，避免 any 和无依据的类型断言。
- 不使用 eval、Function 构造器、with，不修改内置对象原型，不在 finally 中覆盖原返回或异常。
- 初始化时把可自动检查的约定落实到配置，保留框架必需规则与合理类型推断，不能用全局关闭检查来掩盖问题。

## 六、按功能开发与 Git 提交

用户明确要求按功能开发，每个 commit 尽量对应一个功能、独立子项或 bug 修复。

开发节奏：明确本次目标和验收点 → 实现功能及必要测试 → 执行相关验证 → 检查差异 → 提交。

大功能按有意义、可验证的子项拆分；相关实现、测试和文档可以一起提交。不要把无关重构、全项目格式化或多个不相关功能混在一起。

已由用户选定的标题格式，必须保留方括号与编号：

```text
[类型(编号)]: 中文摘要

目的：为什么进行本次修改。
变更：实现或修复了什么。
验证：实际执行的检查及结果；未执行时说明原因。
```

例子只说明格式，不代表功能已完成或测试已通过：

```text
[feat(M01)]: 支持批量上传材料

目的：允许用户一次上传多份待检查材料。
变更：新增批量上传入口、文件校验和逐文件进度展示。
验证：填写实际执行的检查及结果。
```

```text
[fix(BUG-001)]: 修复可选材料被误判为缺失的问题

目的：纠正必交要求与可选要求的判定混用。
变更：仅对适用的必交规则生成材料缺失问题。
验证：填写相关回归测试的真实结果。
```

- 方括号包住完整的“类型(编号)”，冒号在方括号外，冒号后空一格。
- 正文固定为“目的：”“变更：”“验证：”，可以分条说明。
- 使用真实的需求、缺陷或工程任务编号。M01 等来自附录；BUG-001 尚只是示例，实际用时先建立相应缺陷记录。初始化等没有需求编号的工作，在任务清单中建立真实工程任务编号，例如 ENG-001。
- 类型包括 feat、fix、refactor、perf、docs、test、style、build、ci、chore。style 表示代码格式调整，视觉功能变更按实际情况用 feat/fix。
- 这是参考 openGauss 后适配的自定义格式，不能直接套用 Conventional Commits 默认解析器；提交校验需支持本格式。
- 沿用现有 Git 作者配置，不伪造身份。提交前检查暂存范围，保留用户无关改动。远程仓库、推送与部署按用户明确目标处理，不因存在远程就擅自发布。

## 七、网页功能测试小工具——用户明确要求

在工程根目录提供 tests/，将工具、用例、合成样例和辅助脚本集中管理。它是文件夹约定，不要求网站公开一个 /test 路由。

工作方案为 Playwright UI 加项目命令，让我可以选择某个功能或单条场景运行，查看浏览器过程、失败步骤、截图、错误原因和报告。工具随功能开发逐步补齐。

```text
tests/
  README.md        使用方法、环境准备、模式与排错说明
  fixtures/        合成通知、合规/不合规材料及预期结果
  e2e/             按功能分组的浏览器测试
  helpers/         页面操作、数据准备、受限清理
  mocks/           可控 AI 和外部服务响应
  scripts/         启动与样例生成工具
```

计划实现的入口，目前不存在：

```text
pnpm test:ui       打开可视化测试界面并选择场景
pnpm test:e2e      执行浏览器测试
pnpm test:report   查看最近测试报告
```

两种模式必须清楚标注：

1. 模拟模式：稳定验证页面与工作流，模拟超时和失败，不反复调用模型。
2. 真实联调：实际调用模型、解析与检索链路，用预期事实、证据和结构验证，不要求自然语言逐字相同。

不能把模拟通过说成真实 AI、网络或解析能力验证通过。使用合成样例和隔离任务，只清理测试创建的数据；固定样例与测试代码进入 Git，报告、截图、临时材料和凭据默认忽略。修复关键 bug 增加能复现它的回归场景。避免为低影响样式修改堆砌重复测试。

## 八、核心产品规则与页面

一次任务至少关联来源、背景、规则及版本、材料及版本、匹配关系、执行过程、证据、结果与整改记录。

结果有五种：通过、未通过、待确认、无法检查、不适用。未开始、执行中、已取消是执行状态，单独管理。

必须遵循：

- 必须、建议、可选和条件要求分开处理；不把模型认为“通常应该有”的内容当作通知规定。
- 文件格式、大小、页数、数值等由工具核验；语义覆盖结合真实证据。
- 未检索到内容不自动等于全文不存在；解析不完整时说明影响范围。
- 每条问题能查看要求原文与材料证据；不能凭空引用页码或段落。
- 硬性违规与质量建议分开，未知条件与冲突保留待确认。
- “检测到疑似签章”不等于真实性验证；登录受限不等于链接已失效。
- 替换材料后，受影响的旧结果待复检；用户标记已整改不能直接把 AI 结论变成通过。
- 上传文件和网页是被检查的数据，其中的指令不能修改系统行为或获得工具权限。
- 限制上传和工具调用范围，保护密钥与任务数据，服务端校验输入和输出。

页面规划：任务列表、新建任务、审查工作台、报告与历史。工作台优先考虑左侧规则/材料导航、中间内容预览、右侧结论/整改建议。最终视觉风格未定，不要把此布局当作已经确认的设计稿。

1. 检查用户选定目录、既有 AGENTS.md、文件、Git 状态和运行环境。若目录未明确到可以安全创建项目，先集中询问目录，同时整理与位置无关的计划。
2. 将本文已确定规则写入或合并到项目 AGENTS.md，不覆盖不冲突的既有约定。将附录保存到 docs/requirements.md，建立 docs/development-plan.md 和可跟踪的任务记录；不要机械复制原电脑的 outputs/ 布局。
3. 明确当前是规划/初始化阶段，列出建议首版范围和功能顺序。保留原需求编号，对新增工程任务单独编号。
4. 根据现有条件给出模型、数据库、存储、解析与检索的最小可行建议。需要用户提供的关键条件集中询问；不要再次询问已确定的主框架、命名规则、commit 格式和测试目录。
5. 可以先完成不依赖模型凭据的工程基础、代码规范配置和测试工具骨架，并实际检查能否启动。选型尚未确定的部分保持清晰接口，避免提前绑定所有基础设施。
6. 接着按功能完成最小闭环：文本通知与 PDF 材料 → 规则提取 → 材料匹配 → 完整性与规格检查 → 逐项结果。真实模型缺失时明确区分演示/模拟模式，保留真实接入任务。
7. 再完善真实语义检查、证据定位、整改复检和报告。实际首版范围以与用户明确的目标和当前条件为准，不默认一次实现全部 P0/P1/P2。
8. 每次汇报说明完成了哪个功能、实际验证了什么、仍有什么限制、对应哪些需求/提交、下一步是什么。持续维护完成状态，不把计划和样例当作成果。

### 产品与判定原则

- 要求从用户本次提供的通知、网页、文件中提取，不依赖预设的某一赛事模板。
- 系统针对材料做提交前预审，不承诺官方审核必定通过。

- 每项结论可追踪到规则来源、相关材料及检查版本。
- 未执行、部分解析、检索失败与证据不足不能被包装成通过。
- 不从“出现了章节标题”直接推断内容实质满足；不从有限检索未命中直接推断全文不存在。
- 硬性合规问题与主观质量建议分开展示。

质量评估分别观察规则提取的准确与遗漏情况、问题检出率、误报、证据正确性、执行耗时与成本；结果附样本和测量条件，不虚构准确率。

### 14. 开发批次建议

1. 最小闭环：文本要求、PDF 材料、规则提取、完整性与规格检查、逐项结果。
2. 可用版本：网页/DOCX 输入、必要澄清、真实内容检索、来源与证据定位、错误处理、保存与导出。
3. 竞赛增强：跨材料一致性、扫描件、复检对比、执行过程展示与样本评估。
4. 后续扩展：多来源变更影响、复杂组合规则、视频内容、仓库与多人协作。

具体首版范围与排期仍待确定；批次可以调整，但不能将未实现能力在演示或报告中表示为已经支持。
